ray-guard v0.2.0 — say only what was observed

Three corrections to what the report CLAIMS, all of them found by reading the
buyer-facing output as a skeptic rather than by a test going red. None of them
changed what the scanner detects: the demo stack still grades F with 21
findings, 3 critical, 6 high, 6 medium, 3 low, 3 info - verified against the
live stack on 2026-10-31.

If you are on v0.1.1 and plan to hand a report to anyone, upgrade. Every one of
these is a sentence a security lead can correct out loud.

WHAT CHANGED IN THE REPORT

- Four rule titles claimed internet exposure the scanner cannot observe:
  RG-TRITON-002, RG-TORCHSERVE-002 and RG-DCGM-001 said "publicly reachable",
  and RG-BUCKET-001 said "lists publicly". A scan of 172.31.0.0/16 - which is
  what a GPU cluster looks like - made all four factually wrong, in the single
  most-read string in the report. They now say "reachable without
  authentication". "Internet-exposed" is reserved for something independently
  verified, which Level 1 never does.

- The Ray finding separated what was observed from what it means. v0.1.1 said
  "An unauthenticated Ray dashboard is not a hardening gap - it is remote code
  execution", having observed an HTTP 200 on `/`. The consequence is right -
  Ray's Jobs API runs a caller-supplied entrypoint, which is why CVE-2023-48022
  is disputed rather than patched - but we had not observed the Jobs API. The
  report now states the observation, the consequence and what we did not do, in
  that order.

- Grades are scoped to the tier that produced them, and A+ is gone from Level
  1. CLAUDE.md 10.0 defines A+ as "full hardware attestation (CC mode
  cryptographically verified via L3)", and v0.1.1 printed A+ 100/100 for any
  clean scan - a grade whose published meaning is "hardware attested", awarded
  by a port scanner. A clean L1 scan now grades 94/A, the top of the A band,
  and says so: "A is the highest grade a Level 1 assessment can earn." The
  report also prints the matrix it scored against, so the number is
  reconstructable rather than taken on faith. `tier: "L1"` now travels in the
  JSON beside the grade.

WHAT CHANGED IN DETECTION

- RG-RAY-001 identifies the dashboard by an unauthenticated 2xx on
  `/api/version` rather than on `/`. Measured against real Ray 2.9.0: `/`
  returns the dashboard's HTML shell, which any web server answers, while
  `/api/version` returns Ray's own version document.

  This fixed a false positive we had not been looking for. A plain web server
  on 8265 answers 200 on `/` and 404 on the wildcard control, so the control
  never caught it: measured, it was reported as **critical RG-RAY-001, grade
  F**, and is now Info - "no probe identified the service (HTTP 404)".

  Deliberately NOT `/api/jobs/`, which is the read-only sibling of the
  code-execution endpoint and would be stronger evidence. A GET there returns
  each job's `entrypoint` - the customer's literal command line - plus
  `runtime_env`, which can carry environment variables. Requesting the most
  payload-adjacent document on the host only to discard it is not a trade worth
  making for a conclusion `/api/version` already supports (P3). It is also why
  "job" is a forbidden substring in the benign-path allowlist.

  The ceiling, stated: a Ray too old to serve `/api/version` is reported as an
  unidentified service on 8265 at Info rather than as this critical - visible,
  not silent. The nightly real-services job is the guard for that endpoint
  continuing to exist upstream.

- CVE-2025-62593 is version-specific, and the scanner does no version
  detection. The report now says the version was not determined and marks that
  CVE applicable-if-vulnerable rather than as a confirmed finding about the
  host. CVE-2023-48022 stands as before: there is no fixed version to upgrade
  to, so reachability is the entire control.

NEW, AND NOT YET USEFUL TO YOU

The Rego rule library (`/policies`) ships all 19 Level-1 rules as
policy-as-code with the verification sentinels CLAUDE.md 8 requires - 113 OPA
assertions, plus two generated corpora that replay the shipping Go detector
through OPA and require both implementations to agree on what fires and what
closes. There is no control plane behind it yet, so it is auditable material
rather than a feature: "our rules are open-source and readable" is the point.

Two bugs it caught that are worth naming, because both would have ended up
inside a signed credential:

- An unscoped verification sentinel let a Ray observation returning 401 close
  RG-BUCKET-001. "The unauthenticated request was refused" is true of it and
  entirely irrelevant.
- Every sentinel now requires evidence that the host was actually reached. The
  obvious closure for an exposure finding is "the port no longer answers",
  which is equally satisfied by a host nobody reached - a typo, a dark subnet,
  a scan from the wrong side of a firewall. That would have turned "we could
  not look" into "we attest it is fixed".

UNCHANGED

Detection coverage, severities, remediation text, the report's structure, the
exit codes, the JSON field names you may already parse (`tier` is additive),
the zero-dependency static binary, metadata-only enforcement, and no network
egress beyond the targets you name.

VERIFYING THIS RELEASE

Same as v0.1.1: every artifact ships a Sigstore bundle
(`<artifact>.sigstore.json`). Verified end to end with cosign v3.1.3 and the
v3.1.4 the workflow pins; on a 2.x client you may need `--new-bundle-format`,
which we have not tested and would rather say than have fail in front of you.

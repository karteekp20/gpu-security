ray-guard v0.1.1 — the wedge, hardened

Supersedes the v0.1.0 tag, which was pushed eighteen commits ago, before
everything below. Its release was never published - it sat as a draft - so
this is the first release of ray-guard that anyone can download.

What ray-guard is, unchanged: a single static Go binary with no dependencies
that finds exposed and unauthenticated AI orchestrators on a network you are
authorized to assess, then writes a standalone GPU Risk & Isolation Report
(JSON + self-contained HTML). Read-only and benign - one GET per check to a
documented health endpoint, plus one control request per identified port, no
request body, no exploitation. Metadata only: no model weights, prompts,
training data, inference content, or object contents are read, stored, or
transmitted, enforced by a build-blocking test suite. No network egress
beyond the targets you name, enforced by an import guard rather than a flag.

NEW DETECTIONS

- RG-TORCHSERVE-001 (critical) - unauthenticated TorchServe management API,
  CVE-2023-43654 / "ShellTorch". It registers a model from any URL the
  caller names, so reachability is execution. Upstream is archived, so
  network isolation is the durable fix rather than an upgrade.
- RG-TORCHSERVE-002 (low) - TorchServe metrics endpoint reachable.
- RG-SGLANG-001 (high) - unauthenticated SGLang inference API.
- RG-DCGM-001 (medium) - NVIDIA DCGM exporter publicly reachable. Medium
  rather than low because its labels name the pod and namespace using each
  GPU: an exposed exporter is a tenant workload inventory.
- RG-TLS-003 (medium) - obsolete TLS version negotiated (1.0/1.1, RFC 8996).
- Port 8080 is now swept but deliberately never attributed. TorchServe's
  inference API, TGI, LocalAI and most model servers default there, and a
  200 on /ping is not evidence of any of them.

Both Critical rules are now validated against the real software, not mocks.

CORRECTNESS FIXES

Each of these could have produced a confidently wrong report, which is the
worst thing a security tool can do.

- A scan that reached nothing graded A+ with "No exposure was observed". An
  unresolvable hostname, a dark /24 and a genuinely clean host were
  indistinguishable. Clean grades now require at least one host that
  answered; otherwise the grade is N/A and the exit code is 7.
- Only a TCP RST proves a host is alive. "No route to host" arrives promptly
  rather than as a timeout, so treating every non-timeout error as "closed"
  let an empty subnet look like a clean one.
- A server that answers 2xx to everything - an SPA dev server, a catch-all
  ingress route, a captive portal - was reported as whatever orchestrator
  shares its port: a critical "unauthenticated Ray dashboard" on 8265, and
  on 8000 both vLLM and Triton at once. Each identified port now gets one
  control request to a path that cannot exist; a port that answers that too
  is reported as unidentified rather than named.
- Services behind TLS 1.0/1.1 were invisible. Go's client refuses an
  obsolete handshake by default, so the probe concluded "not TLS", spoke
  plaintext to a TLS port, and reported an unauthenticated dashboard behind
  an old terminating proxy as an unidentified open port - with the obsolete
  protocol equally invisible. The scanner now negotiates down to TLS 1.0 for
  measurement and reports the version it got.
- Running out of file descriptors made the scan under-report silently rather
  than fail. Measured with the limit at 128: a /24 graded C with 3 findings
  where the same scan graded F with 19, and the Ray dashboard was reported
  as an unidentified service. Local probe failures (EMFILE and friends) are
  no longer recorded as port states, such a run is marked degraded and
  cannot earn a clean grade, and -concurrency is clamped to what the host
  sustains. What binds is the hard limit: Go raises the soft limit to the
  hard limit at startup, so the low soft defaults are not the case to worry
  about - containers and CI images with a low hard limit are.
- Ctrl-C discarded the entire run. It now stops probing immediately and
  still writes the report for what was reached, marked partial and
  ungradeable, and exits 130. Targets never dialed are absent rather than
  reported as unreachable: "we stopped" is a fact about the scanner, not
  about the customer's host.
- A target that is not a host was accepted and then quietly skipped.
  `-targets https://10.0.0.5:8265,127.0.0.1` - the likeliest paste there is,
  because the dashboard URL is what is in the operator's browser tab -
  recorded the URL as an *unresolved host*, graded the rest A+, and exited
  0. "Unresolved" is also what a real DNS failure looks like, so the one
  line admitting it read as the customer's problem. URLs, host:port, CIDR
  blocks in -targets, trailing `#` comments and malformed addresses are now
  rejected before anything is dialed, each with the host or flag you
  probably meant. A pasted credential is never echoed back.
- A zone-scoped IPv6 target (`fe80::1%eth0`, how a link-local address on a
  management network is written) dialed fine at TCP level, but a URL must
  percent-escape the zone - so every HTTP probe failed to build and the port
  was reported as "open, no HTTP response". An unauthenticated dashboard on
  such an address was an Info-level unidentified port. Found by the new
  -targets fuzz property, fixed, and verified against a real listener.
- A truncated report could exit 0. report.Write deferred its Close() and
  discarded the error.
- A mistyped -buckets entry printed to stderr mid-scan and was then dropped,
  so a bucket in scope went missing from the report. It now exits 2 before
  any probing, as do unwritable -out and -benchmark-snapshot paths: a scan
  that completes and then cannot write has cost a second pass over a
  customer's cluster.
- The lint gate was not enforcing its own configuration. golangci-lint
  action v6 cannot drive a golangci-lint v2 config, so the job reported
  green without reading the file it pointed at. Action bumped to v9, linter
  pinned to v2.14, and the errors the first real run surfaced are fixed
  rather than suppressed.

REPORT AND CLI

- -label puts an engagement name on the report, and the report records the
  host the scan ran from. Neither exists as a field on the anonymized
  benchmark snapshot - omitted by construction, not stripped.
- Exit codes: 0 clean, 1 runtime error, 2 usage error, 3-6 worst severity
  found, 7 no grade (nothing responded, or the measurement was unreliable),
  130 interrupted. 7 and 130 outrank the severity codes: a run with no
  grade has not earned a verdict.
- TLS is classified rather than reported present/absent: self-signed,
  expired, not-yet-valid, hostname-mismatch, plus the negotiated version. A
  bad certificate and an obsolete protocol are separate findings, because
  they have separate fixes.
- Report files are written owner-only (0600/0700). A report lists exactly
  which of a client's services are exposed and unauthenticated; that is the
  wrong thing to default to world-readable.

VALIDATED AGAINST REAL SOFTWARE

The integration suite runs real containers: Ray, Jupyter, MLflow, Ollama,
TorchServe (twice - exposed, and token-protected as a negative control), and
nginx terminating TLS in front of the real Ray dashboard. Real Triton runs
on an opt-in profile (16GB image). vLLM, SGLang, DCGM and CI's Triton remain
fixtures replaying documented response shapes, which the test output states
rather than hides.

What running the real thing falsified, and we corrected:

- TorchServe does have native authentication (token authorization, default
  since 0.12) and answers 400, not 401, when it is required. The
  remediation text said otherwise.
- The official pytorch/torchserve image's bundled config.properties binds
  inference, management, metrics and both gRPC addresses to 0.0.0.0,
  although upstream's security page says these ports are localhost by
  default.
- Triton's metrics server answers 200 on any path, which is normal for an
  exporter and would have silently downgraded RG-TRITON-002.
- Real Jupyter and MLflow accept a connection and then wait silently for a
  complete HTTP request, which used to burn the full probe timeout on every
  plaintext port. Ray rejects a ClientHello in about a millisecond, so no
  mock ever showed this.

GUARANTEES ENFORCED BY TESTS, NOT BY DOCUMENTATION

- The metadata-only suite blocks the build if payload-shaped data can cross
  the collection boundary, structurally and behaviourally. The four leaks
  used to confirm the suite fails are written up inside it.
- An import guard fails the build if any package other than the prober
  gains the ability to open a socket or run a command. "It cannot phone
  home" is a claim about every future version of this binary.
- The three parsers that read operator input (-cidr, -ports, -targets) are
  fuzzed nightly. The properties asserted are the ones that keep a scan
  inside its authorization.

SUPPLY CHAIN

- Every third-party GitHub Action is pinned to a commit SHA rather than a
  mutable major tag. These actions run inside the job that builds and signs
  these binaries, so a repointed tag would have been a direct path to a
  trojaned release. Dependabot keeps the pins current.
- The release workflow's write token is scoped to the release job, and the
  workflow verifies the signatures it just produced before publishing. The
  release body tells you to run cosign verify-blob; that instruction is now
  tested on every release.
- go.mod stays at go 1.22 deliberately. The directive is the minimum needed
  to build, not the newest available: requiring a brand-new toolchain to
  compile an air-gap-oriented binary narrows who can build it offline.

Verify this release yourself:

  cosign verify-blob \
    --bundle ray-guard-linux-amd64.sigstore.json \
    --certificate-identity-regexp '^https://github.com/karteekp20/gpu-security/' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    ray-guard-linux-amd64
  sha256sum -c SHA256SUMS

Still no control plane, database, web console, or trust credential. Those are
Phase 1 and gated on buyer validation, not on engineering readiness.

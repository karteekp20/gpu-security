ray-guard v0.1.1 — correctness and supply-chain fixes

Supersedes v0.1.0, which was tagged before the two fixes below. Use this one.

What ray-guard is, unchanged: a single static binary that detects exposed and
unauthenticated AI orchestrators (Ray, vLLM, Triton, Slurm, MLflow, Jupyter,
Ollama), TLS problems, and publicly listable object storage, then emits a
standalone GPU Risk & Isolation Report. Read-only and benign - one GET per
check to a documented health endpoint, no request body, no exploitation.
Metadata only: no model weights, prompts, training data, inference content, or
object contents are read, stored, or transmitted, enforced by a build-blocking
test suite. No network egress beyond the targets you name.

Fixed since v0.1.0:

- A truncated report could exit 0. report.Write deferred its Close() and
  discarded the error, so a failed flush on close was reported as a successful
  report. The report is the deliverable handed to a security lead; it now
  closes explicitly and returns that error.

- The lint gate was not enforcing its own configuration. golangci-lint-action
  was on v6, which cannot drive a golangci-lint v2 config, so the job reported
  green without reading the file it was pointed at. Action bumped to v9 with
  the linter pinned to v2.14, and the errors the first real run surfaced are
  fixed rather than suppressed.

Supply chain:

- Every third-party GitHub Action is pinned to a commit SHA rather than a
  mutable major tag. These actions run inside the job that builds and signs
  these binaries, so a repointed tag would have been a direct path to a
  trojaned release. Dependabot keeps the pins current.

- The release workflow's write token is scoped to the release job, and the
  workflow now verifies the signatures it just produced before publishing
  anything - the release body tells you to run cosign verify-blob, and that
  instruction is now tested on every release.

- go.mod stays at go 1.22 deliberately. The directive is the minimum needed to
  build, not the newest available, because requiring a brand-new toolchain to
  compile an air-gap-oriented binary narrows who can build it offline.

Verified against real services: Ray, Jupyter, MLflow and Ollama run as actual
containers in the integration suite, not mocks. vLLM and Triton ship GPU-only
images and remain labelled fixtures, which the test output states rather than
hides.

Still no control plane, database, or trust credential. Those are Phase 1 and
gated on buyer validation, not on engineering readiness.

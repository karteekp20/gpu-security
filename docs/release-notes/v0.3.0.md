ray-guard v0.3.0 — show the evidence, and withdraw a claim

This release exists because v0.2.0 asserts a CVE it cannot support. If you are
on v0.2.0 and plan to hand a report to anyone, upgrade before you do.

Everything else here makes the report say what its conclusions rest on: the
evidence behind each finding, the hosts that answered and raised nothing, the
settings the scan was measured with, and the grading scale with the band this
tier cannot award. Detection coverage is unchanged - the demo stack grades F
with 21 findings, 3 critical, 6 high, 6 medium, 3 low, 3 info, before and
after, re-verified against the live stack on 2026-11-06.

THE CLAIM BEING WITHDRAWN

v0.2.0's report asserts CVE-2023-43654 (ShellTorch) against TorchServe. NVD
bounds that CVE at versionEndExcluding 0.8.2, and the host under test runs
0.12.0 - four minor versions past the fix. So the released report carried a
false CVE claim about a host that is not affected by it, refutable in the room
by an operator typing `pip show torchserve`.

The citation does not disappear, because dropping it would be the opposite
error. NVD's 0.8.2 bound records when a startup *warning* was added, not a
behaviour change: the 0.12.0 official image still logs "can access any URL to
load models" on boot, with allowed_urls unset in its own config.properties. So
the CVE moves to a separate field:

- `cves` now holds only CVEs whose condition is the condition we observed.
- `cves_unconfirmed` holds a CVE whose advisory names a fixed version, with
  that version verbatim and the check that would settle it. RG-TORCHSERVE-001
  now asserts no CVE at all.

The discriminator is written down once and enforced: if the advisory names a
fixed version, a tier that does not determine versions cannot assert it. Level
1 decides every rule from a status code and reads no response bodies, so it
never learns a version. The asserted list is checked against a table of what
each advisory says, recorded independently of the rule table, so a CVE added
because it is famous fails the build until someone looks it up.

Worth stating plainly: the Ray pair had the same defect wearing a better
disguise. Real Ray is 2.9.0, genuinely below CVE-2025-62593's 2.52.0 fix, so
that claim happened to be true - by luck, because the scanner never read the
version. Being right without evidence is not a property a verifiability vendor
can sell.

Severities and the grade are unchanged by design. RG-TORCHSERVE-001 is Critical
on what was observed - a management API that registers a model from any URL the
caller names - never on the CVE. Had removing a CVE moved a grade, the grade
was resting on the wrong thing.

WHAT CHANGED IN THE REPORT

- Every finding carries the evidence it rests on: a level (the verification
  ladder, always `observed` at Level 1, stated so the ceiling is visible) and a
  basis - how the subject was identified. service_api means the service's own
  API answered and a wildcard control confirmed the path discriminates;
  metrics_endpoint means a conventional /metrics path answered, which is weaker
  because exporters answer on any path; generic_path means only a root page
  answered, which any web server does; port_only is TCP reachability and
  nothing more; transport is observed in the TLS handshake. The path that
  produced the identification travels with it, so a reader can re-run the
  request.

  Measured on the demo stack: of 21 findings, 8 are service_api, 6 port_only, 4
  metrics_endpoint, 2 transport - and exactly one is generic_path,
  which is MLflow. Before this field, MLflow-on-"/" and Ollama-on-"/api/tags"
  looked equally well-evidenced, and a security lead who spot-checks one
  finding before trusting the rest had no way to tell which was the weak one.

  The basis is derived from the probe table rather than declared per rule, so
  moving a probe path changes it and fails the build until the rule library
  agrees. A constant saying service_api keeps saying it after someone points
  the check at "/".

- An exposure map: one row per host that answered, one column per port probed,
  each cell the worst finding there with a severity letter as well as a colour.
  The hosts that answered and raised nothing are drawn as rows of empty cells,
  which is the point - a findings list cannot show them, and they are the
  answer to "does this thing flag everything it touches?". On the demo stack 2
  of 15 responders are clean, and one is running a Ray dashboard bound to
  loopback: same software, same port, same rule as the flagship Critical,
  opposite answer, because the only thing that differs is reachability.

  This required retaining the responded host list, which the report never kept.
  v0.2.0 could say "15 responded, 13 had findings" and could not say which two
  were clean - a clean responded host was unrecoverable from the artifact, and
  it is the only positive evidence this tier produces. `responded` is additive
  to report.json.

  A blank cell is not a closed port, and the chart says so in words: a port can
  be open, answer nothing we recognise, and raise no finding. Above 40 rows the
  worst are kept and the note states how many were not drawn.

- A coverage bar: one stacked bar - responded, no response, unresolved, probe
  failed, not probed - with a sentence above it carrying every count and a note
  below saying what it means for the grade. Counts, never percentages, and
  every state present at all is drawn wide enough to see: one unassessed host
  in a /24 renders at 2.36 of 600 units otherwise, and a coverage gap drawn as
  nothing is the defect the chart exists to prevent.

- A grade band strip above the scoring matrix: the scale with the band this
  scan landed in filled, and the A+ band drawn, hatched, and labelled "L3
  only". A+ is visible rather than omitted on purpose - a reader comparing an A
  against a scale that stops at A learns nothing; one comparing it against a
  visible, explicitly unavailable A+ learns the actual claim. There is no
  needle: the matrix returns a representative score per band, not a
  measurement, so a pointer at "40 of 100" would claim precision we do not
  have. An inconclusive run draws no scale at all, because N/A is not a
  position on it.

- The report records the settings it was measured with - probe timeout, the
  concurrency actually used, the resolved port set, and the scope as it was
  typed - in `parameters` in the JSON and a table under Scope & method. Every
  coverage line is a claim about a duration: "no response" at -timeout 1s and
  the same line at 5s are different observations of the same host, and a reader
  holding the report could not tell which they had. The clamp is no longer
  invisible either - under a low open-file limit, -concurrency 64 ran at 2 with
  the report saying nothing about it; both numbers are now recorded.

WHAT CHANGED IN DETECTION

One correctness fix, and it can change your exit code.

A hostname is now resolved once and every probe for it is pinned to that
address, and the report states the address it dialed. Before, the scanner
resolved a name only to decide whether to proceed, threw the addresses away,
and passed the name to every dial - so the resolver answered again per
connection and a round-robin name was probed at a different machine from port
to port, while the report recorded only the name and had no field for an
address.

The consequence worth flagging: a name that resolves to several addresses now
discloses the ones it did not probe and cannot earn a clean grade - N/A, exit
7. Probing one of three nodes and printing A claims the name is clean. If you
script on exit codes and scan multi-address names, this is the change to read.
Pass the addresses individually to assess them all.

Pinning deliberately does not change identity: the name stays in the URL, the
Host header, SNI and the certificate check, because dialing an address and
verifying against it would turn a valid certificate into a hostname-mismatch
finding and would ask a name-based virtual host for the wrong site.

JSON CHANGES, ALL ADDITIVE

Top level: `parameters`, `responded`. Per finding: `evidence`,
`cves_unconfirmed`. Nothing was renamed or removed.

`cves_unconfirmed` is a new field rather than a retyped `cves` on purpose: the
naive read .cves[] becomes true instead of breaking, which is the right
failure direction for a SIEM - silently under-reporting beats garbling - and
the qualification lives in the field name, so a consumer that flattens the
document cannot drop it.

UNCHANGED

Detection coverage, severities, remediation text, the exit codes other than the
multi-address case above, the zero-dependency static binary (go.mod still has
no require block), metadata-only enforcement, read-only probing, and no network
egress beyond the targets you name.

VERIFYING THIS RELEASE

Every artifact ships a Sigstore bundle (<artifact>.sigstore.json). Verified end
to end with cosign v3.1.3 and the v3.1.4 the workflow pins. On a 2.x client you
may need --new-bundle-format; we have not tested a 2.x client and would rather
say so than have it fail in front of you.
